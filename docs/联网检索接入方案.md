# 联网检索接入方案（SearXNG + Firecrawl，浏览器兜底）

> 状态：**P2 已落地**（2026-08-12 dev 环境全链路验证通过：compose 起服务 → 插件层搜索/抽取实测返回结果）
> 关联文档：`docs/前后端对接规划-不含知识库.md`（P2 条目"Web 检索"）、`docs/改造计划.md`
> 最后更新：2026-08-12

## 1. 目标与原则

让智能体具备"查资料并回答问题"的能力，同时守住 to-B 硬约束：

- **不出域**：搜索与抽取全部走客户部署内的自托管服务，不调用任何 SaaS API（Tavily/Exa 等云端 provider 不启用）。
- **最小改动**：仓库已内置完整的 web provider 插件体系，本方案只做"配置 + 接线"，不改核心文件。
- **能力分级**：搜索/正文抽取是主路径；浏览器自动化只作为"操作网站"场景的 P3 兜底，不为查资料服务。

## 2. 总体架构

```
用户提问
   │
   ▼
web_search（SearXNG，元搜索聚合）          ← 定位：答案在哪个网页
   │  返回 [{title, url, description} × N]
   ▼
web_extract（Firecrawl 自托管，渲染+正文清洗） ← 阅读：把网页正文拿回来
   │  返回 [{url, title, content(markdown)}]
   ▼
模型综合正文作答（正文经注入防护后进入上下文）

P3 兜底（仅"操作网站"类需求，本期不实施）：
browser_navigate 等浏览器工具（plugins/browser/browser_use，本地无头 Chromium）
```

### 为什么是两个组件而不是一个

| | SearXNG | Firecrawl |
|---|---|---|
| 输入 | 查询词 | 具体 URL |
| 输出 | 标题 + URL + 一两行摘要 | 完整正文（markdown，去广告/导航） |
| 本质 | 元搜索引擎（聚合上游引擎结果） | 网页抓取器（渲染 JS、抽取正文） |
| 短板 | 不抓页面内容 | 不能搜索 |

二者是串联关系：搜索管定位，抽取管阅读。SaaS 二合一方案（Tavily/Exa）因"不出域"约束排除。

## 3. 现状盘点（仓库已有件）

| 环节 | 已有件 | 说明 |
|---|---|---|
| 搜索 provider | `plugins/web/searxng/` | SearXNG JSON API 客户端，`SEARXNG_URL` 配置即启用，无需 key |
| 抽取 provider | `plugins/web/firecrawl/` | 自托管时设 `FIRECRAWL_API_URL`，无需 key；已内置跳转目标 SSRF 检查 |
| 工具注册 | `tools/web_tools.py` | `web_search`/`web_extract` 已注册；`check_fn=check_web_api_key`，未配置后端时工具自动对模型隐藏 |
| 工具集 | `toolsets.py` | 已有 `"web": ["web_search", "web_extract"]` |
| SSRF 防护 | `tools/url_safety.py` | 默认拦截内网/元数据地址（169.254.169.254 等永远拦截）；`security.allow_private_urls` 可显式放行 |
| 浏览器兜底 | `plugins/browser/browser_use` + `browser_navigate` 等 | P3 备用；工具描述内置"优先 web_search"引导（`model_tools.py:463`） |

**唯一缺口**：`server/tool_policy.py` 的 headless 工具策略目前只放行 `db`/`terminal`，`web` 工具集未接入。

## 4. 镜像构建方案

### 4.1 镜像清单（已按 2026-08-11 拉取结果锁定 digest，见 docker-compose.yml）

| 服务 | 镜像 | 作用 | 资源量级 |
|---|---|---|---|
| searxng | `searxng/searxng@sha256:cd22dbf7…` | 元搜索引擎 | 轻（258MB） |
| firecrawl-api | `ghcr.io/firecrawl/firecrawl:2.10.19-production@sha256:50446cbc…` | 抓取 API（harness 同容器内置 worker） | 中（1.09GB） |
| firecrawl-playwright | `ghcr.io/firecrawl/playwright-service@sha256:468009ba…` | JS 渲染微服务 | 重（1.43GB，含 Chromium） |
| firecrawl-redis | `redis:7.2.15-alpine`（与主栈同镜像） | Firecrawl 队列/限流 | 极轻 |
| firecrawl-nuq-postgres | `ghcr.io/firecrawl/nuq-postgres@sha256:aed86f62…` | Firecrawl NuQ 队列库（含 pg_cron） | 中（455MB） |
| firecrawl-rabbitmq | `rabbitmq:3-management@sha256:e582c0bc…` | Firecrawl NuQ 消息通道 | 轻（252MB） |

> 实施时核对结论（与旧资料的三处差异）：
> 1. Firecrawl 镜像组织已从 `mendableai` 迁至 **`ghcr.io/firecrawl`**；`firecrawl` 主镜像有版本 tag（锁 `2.10.19-production`），`playwright-service`/`nuq-postgres` **只有 latest**，按 digest 锁定。
> 2. 新版官方编排是 **api（harness 内置 worker）+ playwright-service + redis + rabbitmq + nuq-postgres** 五件套；FoundationDB 为实验可选项（`NUQ_BACKEND=fdb`），不用。
> 3. **nuq-postgres 的 POSTGRES_USER/POSTGRES_DB 必须保持 `postgres`/`postgres`**：镜像内 pg_cron 绑定 `cron.database_name=postgres`，改库名会导致建表脚本（`010-nuq.sql`）整体失败、api 崩溃循环（`relation "nuq.queue_crawl_finished" does not exist`）。

**版本锁定纪律**（对齐 AGENTS.md 依赖固定政策）：

- 交付镜像**禁止 `:latest`**，全部锁到具体 tag 或 digest（`image@sha256:...`）。
- 升级镜像 = 一次显式的交付动作：先在测试环境验证搜索/抽取回归，再改 tag。

### 4.2 联网环境：直接拉取

客户环境可访问公网镜像仓库时，直接在 `docker-compose.yml` 增加服务（见 §4.4），`docker compose pull && docker compose up -d` 即可。

### 4.3 离线/内网交付：镜像离线包（on-prem 常见）

客户环境完全离线时，在交付机上预构建离线包：

```bash
# 交付机（有网）执行：拉取并锁定版本后打包
docker pull searxng/searxng:<tag>
docker pull ghcr.io/mendableai/firecrawl:<tag>
docker pull ghcr.io/mendableai/firecrawl-playwright:<tag>
docker pull redis:7-alpine

docker save searxng/searxng:<tag> \
            ghcr.io/mendableai/firecrawl:<tag> \
            ghcr.io/mendableai/firecrawl-playwright:<tag> \
            redis:7-alpine | gzip > hermes-web-search-images-<版本>.tar.gz

# 客户现场（离线）执行：
gunzip -c hermes-web-search-images-<版本>.tar.gz | docker load
docker compose up -d
```

随包附带 `SHA256SUMS`（对 tar.gz 逐字节校验）与镜像 digest 清单，客户验收时比对。

### 4.4 compose 编排（已实现，见仓库根 `docker-compose.yml`）

核心安全设计：**检索组件只挂既有的 `hermes-egress` 网络**——可出公网、可被 hermes-server/worker 访问，但够不到 `hermes-data` 上的业务库（mysql/redis）。

已实现的要点（与本文档早期草案的差异）：

- 检索服务归入 **`search` profile**：`docker compose --env-file .env.compose --profile search up -d`，默认 `up` 不会拉起 3.5GB 的检索栈（与 app/agent profile 的既有约定一致）。
- 宿主机仅绑定 127.0.0.1 调试端口：SearXNG `SEARXNG_PORT=18080`、Firecrawl `FIRECRAWL_API_PORT=13002`；redis/nuq-postgres/rabbitmq 不暴露宿主机。
- RabbitMQ 显式建账号（`RABBITMQ_DEFAULT_USER/PASS`）——默认 guest 用户仅允许 localhost 连接，跨容器会拒绝。
- Firecrawl playwright 服务沿用官方加固：`no-new-privileges`、`cap_drop: ALL`、tmpfs 缓存；`BLOCK_MEDIA=true` 省出网带宽。

### 4.5 SearXNG 配置（已实现，`deploy/searxng/settings.yml`）

关键项：

```yaml
use_default_settings: true
search:
  formats: [html, json]   # ⚠️ 必须显式开 json：provider 调 /search?format=json，默认只开 html 会 403
server:
  secret_key: "__SEARXNG_SECRET_KEY__"  # 占位符，启动时由 entrypoint 包装脚本从 compose 环境变量注入
  limiter: false          # 容器内网服务，关闭限流（limiter 依赖 redis）
outgoing:
  request_timeout: 5.0    # 收敛上游超时，避免长尾拖住 agent loop
  max_request_timeout: 10.0
```

实施中踩过的两个坑（已在 compose/settings 中解决）：

1. **secret_key 注入**：searxng 官方 entrypoint 只在"从零生成 settings.yml"时才替换占位密钥；挂载自带配置则不会。compose 里用 entrypoint 包装脚本把 `SEARXNG_SECRET_KEY`（存 `.env.compose`）sed 进**容器内 /tmp 副本**（`SEARXNG_SETTINGS_PATH` 指向它），配置目录以**只读**挂载——保证仓库里的 settings.yml 永远只有占位符，真实密钥不会落进 git。
2. **引擎本地化**（2026-08 实测）：默认启用的 general 引擎全部偏欧美，本部署网络不可达（google/brave/duckduckgo/startpage 超时或人机验证）。已关闭它们，改用国内可达的 **sogou / 360search / bing / baidu**；quark 引擎在本版本稳定崩溃已关闭；baidu 对容器出口 IP 常弹 CAPTCHA，由 SearXNG 自动熔断、保留观察。客户网络环境不同时改 `engines:` 列表即可。

### 4.6 可选：自建镜像（供应链管控更严的客户）

如对第三方镜像有审计要求，可用 Dockerfile 二次封装（固定 base digest + 打入客户证书/代理配置）：

```dockerfile
FROM searxng/searxng@sha256:<digest>
COPY settings.yml /etc/searxng/settings.yml
```

## 5. 配置接线（对 hermes 侧的改动）

全部改动均为配置 + 一行策略代码，不触碰核心文件：

**① `$HERMES_HOME/.env` 追加**（沿用上游既有配置键，非新增 HERMES_* 变量）：

```bash
# 容器化部署（server 跑在 compose 里，走服务名）：
SEARXNG_URL=http://searxng:8080
FIRECRAWL_API_URL=http://firecrawl-api:3002
# dev 环境（server 跑在宿主机，走 127.0.0.1 映射端口，.hermes-dev/.env 已配好）：
# SEARXNG_URL=http://127.0.0.1:18080
# FIRECRAWL_API_URL=http://127.0.0.1:13002
```

**② `$HERMES_HOME/config.yaml` 追加**（`.hermes-dev/config.yaml` 已配好）：

```yaml
web:
  search_backend: searxng     # 搜索后端（web.backend 的共享回退是 web.search_backend… 见 registry）
  extract_backend: firecrawl  # 抽取后端
```

**③ `server/tool_policy.py`**（唯一代码改动，已落地）：

```python
if normalized_mode in {"chat", "plan"}:
    return ["db", "web"]            # Chat/Plan 只读检索，符合 Chat 只读定位
if permission_mode == "full":
    return ["db", "terminal", "web"]
return ["db", "web"]
```

门控逻辑自动生效：未配置 `SEARXNG_URL`/`FIRECRAWL_API_URL` 时 `check_fn` 不通过，工具不出现在 schema 里，模型不会幻觉调用。工具集在每次 `/chat` 请求构建 AIAgent 时解析，无会话中切换，不违反 prompt caching 不变量。

## 6. 安全设计

1. **SSRF**：抽取环节的抓取目标不可信。两道防线：①`tools/url_safety.py` 默认拦截内网/元数据地址（保持默认，不要开 `security.allow_private_urls`）；②compose 网络隔离（§4.4），即使绕过应用层检查，检索容器也够不到业务网段。
2. **Prompt injection**：网页正文是不可信输入。接入时验证 `web_extract` 结果经过 `agent/message_sanitization.py` 的边界标记/清洗路径后再进上下文。
3. **审计**：搜索与抽取属于"外部访问"，需进入 `server/audit.py` 审计流（query、URL、时间、user_id）。落地时以一次真实调用验证审计记录完整。
4. **用量与超时**：沿用工具默认 limit/char_limit；SearXNG 上游引擎超时在 settings.yml 收敛，避免长尾请求拖住 agent loop。
