# 跨会话语义记忆 —— 工程落地方案

> 配合 [`项目架构详解.md §4.2`](项目架构详解.md)（上下文压缩）与 [`改造计划.md`](改造计划.md)（决策 7：无云记忆 / 无出站遥测）阅读。
> 本方案是「给 to-B 高级用户做跨会话语义记忆」的工程落地，不含长会话压缩（见 §9，独立轴）。

---

## 1. 背景与目标

- **现状**：to-B 的记忆是 `server/memory.py` 的 per-user SQLite（`memory.db`），两张表 `memories` + `memory_candidates`；读取时 `list_memory_contents(user_id)` **全量注入** ephemeral system prompt。AIAgent 自带的 MEMORY.md/USER.md 文件式记忆系统被 `skip_memory=True` 关掉。
- **问题**：记忆条数一多，全量注入既费 token 又会冲淡相关性；而且没有「按这轮问题语义召回最相关几条」的能力。
- **目标**：在不破坏「显式存 / 候选审批」人在环流的前提下，给记忆加 **embedding + top-k 语义召回**；存储从 SQLite 迁到 **PostgreSQL + pgvector**；embedding 模型**本地自托管**（守决策 7：无出站）。

> **一句话总结**：保留现有「人审批」流程不动，只换底（SQLite→Postgres+pgvector）+ 换检索（全量注入→top-k 语义召回），embedding 本地跑。

---

## 2. 关键决策（摘要 + 理由）

| 决策 | 选择 | 理由 |
|---|---|---|
| 记忆架构路线 | **扩 `server/memory.py` + embedding**（不复活 memory-provider ABC） | ABC 是为长生命周期 agent 设计的，跟 to-B「每请求新 agent」打架；多用户隔离、改动量、可控性 B 都更优 |
| 主存储 | **PostgreSQL + pgvector** | 结构化 + 向量同库，单租户 per-customer 友好，生态最成熟 |
| 图数据库 | **暂不上**，未来按需（Postgres+Apache AGE 优先于 Neo4j） | 多数用户记忆不是图形状；先别背图库运维开销 |
| Embedding 模型 | **本地自托管**（`bge-m3` 起步） | 守决策 7「无出站」；语义检索 ≠ 必须调云端 embedding API |
| 写入流程 | **保留显式存 + 候选审批**（不引入 LLM 自动抽取） | to-B 合规与可审计优先；自动抽取是后续可选增强 |
| 长会话压缩 | **独立轴，不在本期** | 记忆=跨会话事实召回，压缩=单会话上下文管理，两件事别混 |

> **一句话总结**：B 路线 + Postgres/pgvector + 本地 embedding + 保留人审批 + 长会话另开。

## 3. 现状（代码事实）

| 位置 | 现在做的事 |
|---|---|
| `server/memory.py` | SQLite（`memory.db`）：`memories(id,user_id,content,created_at)` + `memory_candidates(...)`；`save_memory` / `list_memory_contents` / `save_memory_candidate` / `approve_memory_candidate` |
| `server/agent_factory.py:55` | `list_memory_contents(user_id)` 全量 → 拼成 "Persistent memory about this user..." → `ephemeral_system_prompt` |
| `server/routes/memory.py` | `GET/POST/DELETE /memory`（显式存/列/删） |
| `server/routes/chat.py:123` | 每轮结束 `save_memory_candidate(user_id, session_id, user_msg, assistant_msg)` → pending |
| `run_agent.py` / `agent_factory.py` | `skip_memory=True`，AIAgent 的文件式记忆（MEMORY.md/USER.md）系统关闭 |

**三条硬约束（改代码时逐条守）**：
1. **无云记忆 / 无出站遥测**（决策 7）→ embedding 必须本地，记忆数据不出客户环境。
2. **`.env` 只放 secret**；行为配置走 `config.yaml` / `deployment.yaml`，**不新增 `HERMES_*` 非密钥 env**。
3. **prompt cache 神圣**→ 记忆只在 ephemeral_system_prompt 里动（本来就是），不改 cached system prompt、不中途换。

## 4. 目标架构

```
                    ┌──────────────────────────────────────────┐
  /chat 请求 ──────▶│  server/agent_factory.build_agent         │
                    │    query = 当轮 user message              │
                    │    memories = memory.recall(user_id, query)│  top-k 语义召回
                    │    → 注入 ephemeral_system_prompt         │
                    └───────────────┬──────────────────────────┘
                                    │
                    ┌───────────────▼──────────────────────────┐
                    │  server/memory.py  (backend 抽象)         │
                    │   SqliteMemoryBackend  (dev / 回退)       │
                    │   PostgresMemoryBackend (生产)            │
                    └───────┬───────────────────────┬──────────┘
                            │                       │
                ┌───────────▼──────────┐ ┌──────────▼────────────┐
                │  Postgres + pgvector │ │  本地 embedding 服务   │
                │  memories(embedding) │ │  (bge-m3, 进程内/sidecar)│
                └──────────────────────┘ └───────────────────────┘

  写入：POST /memory（显式） 或 候选 approve ──▶ 算 embedding ──▶ 存 Postgres
  每轮：chat.py save_memory_candidate ──▶ pending ──▶ 用户审批 ──▶ approve ──▶ 算 embedding ──▶ 存
```

> **一句话总结**：写时算 embedding 存进 Postgres；读时拿当轮用户消息做 query，top-k 召回相关记忆注入 prompt；backend 抽象让 dev 仍能用 SQLite。

## 5. 存储设计（PostgreSQL + pgvector）

### 5.1 表结构

```sql
-- 启用扩展（每个客户库执行一次）
CREATE EXTENSION IF NOT EXISTS pgvector;

CREATE TABLE IF NOT EXISTS memories (
  id            BIGSERIAL PRIMARY KEY,
  user_id       TEXT NOT NULL,
  content       TEXT NOT NULL,
  embedding     vector(1024),           -- 维度随 embedding 模型定（bge-m3 = 1024）
  kind          TEXT,                   -- fact / preference / event / context（可空，先不强制）
  confidence    REAL NOT NULL DEFAULT 1.0,
  created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
  last_used_at  TIMESTAMPTZ,            -- 命中召回时更新，供 forgetting 用
  source        TEXT,                   -- explicit / candidate（来源追溯）
  disabled      BOOLEAN NOT NULL DEFAULT FALSE   -- 软删除（forgetting 用），不真删
);

-- 向量索引（余弦相似度）。lists 调到约 sqrt(行数)，起步 100
CREATE INDEX IF NOT EXISTS idx_memories_embedding
  ON memories USING ivfflat (embedding vector_cosine_ops) WITH (lists = 100);

-- 每用户按时间倒序（全量注入回退 + forgetting 扫描用）
CREATE INDEX IF NOT EXISTS idx_memories_user_time
  ON memories (user_id, created_at DESC);

-- memory_candidates 保留现有形态（候选不向量；approve 时才算 embedding）
CREATE TABLE IF NOT EXISTS memory_candidates (
  id              TEXT PRIMARY KEY,          -- 沿用 uuid 字符串
  user_id         TEXT NOT NULL,
  session_id      TEXT NOT NULL,
  user_message    TEXT NOT NULL,
  assistant_message TEXT NOT NULL,
  status          TEXT NOT NULL,             -- pending / approved / rejected
  created_at      REAL NOT NULL,             -- 沿用 epoch 秒，迁移省心
  decided_at      REAL,
  memory_id       BIGINT                     -- 指向 memories.id
);
CREATE INDEX IF NOT EXISTS idx_cand_user_status
  ON memory_candidates (user_id, status, created_at);
```

> **注意**：记忆库 Postgres **和只读业务库（`db_query` 目标）是两个不同的库**——业务库只读（GRANT 层强制），记忆库要可写。两者凭据分开。

### 5.2 语义召回 SQL（top-k）

```sql
-- :query_emb 是当轮用户消息的 embedding；:uid 是 user_id；:k 默认 8
SELECT id, content, kind, confidence,
       1 - (embedding <=> :query_emb) AS score   -- <=> 是余弦距离，1-距离=相似度
FROM memories
WHERE user_id = :uid
  AND disabled = FALSE
  AND confidence >= :min_confidence              -- 默认 0.3
ORDER BY embedding <=> :query_emb
LIMIT :k;
```

### 5.3 从 SQLite 平迁

`scripts/migrate_memory_sqlite_to_postgres.py`（新建）：
1. 读 `memory.db` 的 `memories` 全表。
2. 对每条 `content` 调本地 embedding 算向量。
3. `INSERT INTO memories(user_id, content, embedding, source, created_at)`，`created_at` 由 epoch 秒转 `TIMESTAMPTZ`。
4. `memory_candidates` 原样搬。
5. **校验**：迁完比对行数 + 抽样人工核对。

> **一句话总结**：memories 加 `embedding`/`kind`/`confidence`/`last_used_at`/`disabled` 列；检索用 `<=>` 余弦距离 top-k；候选表不动；写一个平迁脚本 + 行数校验。

## 6. Embedding 服务（本地自托管）

### 6.1 模型选型

| 模型 | 维度 | 中文 | 体积 | 备注 |
|---|---|---|---|---|
| **bge-m3**（推荐起步） | 1024 | 优秀 | ~2.3GB | 多语 + 中文强；也可做稀疏/重排 |
| m3e-large | 1024 | 优秀 | ~1.3GB | 纯中文经典选择 |
| Qwen3-Embedding-8B | 4096 | 优秀 | ~16GB | 效果顶、重；用户户余力足再上 |
| nomic-embed-text | 768 | 一般 | ~0.5GB | 轻、英文为主 |

> **起步选 `bge-m3`**：中文场景表现好、维度适中、可本地跑。模型文件放客户环境内，**首次部署时随交付包下发**，不联网下载。

### 6.2 部署形态（二选一）

- **起步：进程内**（推荐先这个）。在 server 进程里用 `sentence-transformers` 加载模型，`server/embedding.py` 暴露 `embed(texts: list[str]) -> list[list[float]]`。简单、无第二个服务。10–50 用户规模够用。
- **加压后：sidecar**。把 embedding 抽成一个小 HTTP 服务（FastAPI + sentence-transformers，或用 `text-embeddings-inference` 容器），server 经 HTTP 调。便于独立扩缩容、隔离模型加载的内存。

### 6.3 Fail-open（关键）

embedding 服务挂了**不能挡住对话**：
- 写入时算 embedding 失败 → 记忆照存（`embedding = NULL`），后台重试补。
- 召回时 embedding 失败 → **回退到「按时间倒序取最近 N 条」**（等价于今天全量注入的子集），告警但不报错。

```python
# server/embedding.py 草图
def embed_texts(texts: list[str]) -> list[list[float] | None]:
    try:
        return _model.encode(texts).tolist()      # 进程内
    except Exception as exc:
        logger.warning("embedding failed, fail-open: %s", exc)
        return [None] * len(texts)                 # 调用方按 NULL 处理
```

> **一句话总结**：起步 `bge-m3` 进程内跑；embedding 任何环节失败都 fail-open（写入留空补、召回回退到按时间），绝不阻塞对话。

## 7. 代码改造（文件级）

### 7.1 新增

| 文件 | 职责 |
|---|---|
| `server/memory_backend.py` | `MemoryBackend` 协议（`save / recall / list / delete / save_candidate / approve_candidate / ...`）+ `SqliteMemoryBackend`（现有逻辑搬过来）+ `PostgresMemoryBackend`（psycopg3 实现） |
| `server/embedding.py` | `embed_texts()` 本地 embedding 客户端（进程内 / sidecar 两实现 + fail-open） |
| `scripts/migrate_memory_sqlite_to_postgres.py` | 平迁脚本 |

### 7.2 修改

**`server/memory.py`** —— 改成调 backend，加 embedding：

```python
# 写入时算 embedding（显式存 + 候选 approve 两条路都过）
def save_memory(user_id, content, *, source="explicit"):
    vec = embedding.embed_texts([content])[0]     # fail-open 可能返回 None
    return _backend.save(user_id, content, embedding=vec, source=source)

# 读取改成「按 query 做 top-k」，但小集合回退全量
def list_memory_contents(user_id, *, query: str | None = None, top_k=8, full_threshold=12):
    memories = _backend.list(user_id)             # 先拿全量计数
    if len(memories) <= full_threshold or query is None:
        return [m.content for m in memories]      # 小集合/无 query：全量（等同今天）
    qvec = embedding.embed_texts([query])[0]
    if qvec is None:
        return [m.content for m in memories]      # embedding 挂 → 全量回退
    hits = _backend.recall(user_id, qvec, top_k=top_k)
    _backend.touch_last_used([h.id for h in hits])  # 更新 last_used_at（forgetting 用）
    return [h.content for h in hits]
```

> **小集合回退全量**是个有意的折中：记忆条数少时，语义召回不如全量准（甚至召回错）；条数多时才切 top-k。避免「为了语义而语义」。

**`server/agent_factory.py:55`** —— 把当轮用户消息当 query：

```python
memories = list_memory_contents(user_id, query=user_message)   # 原来没传 query
```
（`user_message` 是 build_agent 能拿到的本次输入；若拿不到，退化为 `query=None` 全量。）

**`server/routes/memory.py`** —— 显式存/列/删的 HTTP 接口签名不变（内部走新 backend）。

**`server/app.py`** —— `create_app()` 里 `memory_module.init_db()` 改成按配置初始化对应 backend（SQLite 或 Postgres）。

### 7.3 driver 选型

- 用 **psycopg3**（同步），匹配现有 sqlite3 的同步风格；不起 ORM（保持轻、和现有 raw-sql 一致）。
- 连接池：`psycopg_pool.ConnectionPool`，每请求借/还。

> **一句话总结**：抽 `MemoryBackend`（SQLite/Postgres 两实现）+ 新增 `embedding.py`；`memory.py` 写时算向量、读时 top-k（小集合回退全量）；`agent_factory` 把当轮消息当 query；psycopg3 同步、连连接池。

## 9. 长会话压缩（独立轴，另立专项）

**问题**：`agent_factory` 把 session 全历史原样塞进 `prefill_messages`，历史一长撑爆窗口；而 `context_compressor` 只在单个 AIAgent 的 `run_conversation` 内部触发，**管不到请求外的 prefill**。

**两条解法（本期只设计、不实现）**：
1. **DB 侧历史压缩**：`get_messages_as_conversation` 只返回「近期 N 轮原文 + 更早的摘要」，旧轮 `active=0` 软归档（思路同 compression 的 `in_place`）。需要一张 session 级摘要表。
2. **加载时过 compressor**：在 `agent_factory` 拼 prefill 后、交给 AIAgent 前，过一遍 `context_compressor`。

> **一句话总结**：长会话 = 单会话内的上下文管理，跟「跨会话记忆」是两件事；prefill 现在没有压缩是已知缺口，另开专项，不塞进本期。

## 10. 分阶段落地路线（每阶段可独立回退）

- [ ] **Phase 0｜backend 抽象（零行为变化）**
      抽 `MemoryBackend`，把现有 SQLite 逻辑搬进 `SqliteMemoryBackend`；`server/memory.py` 改调 backend。**行为完全不变**，全测试通过即收工。
- [ ] **Phase 1｜Postgres backend + 平迁**
      实现 `PostgresMemoryBackend`（先**不含** embedding 列）；写平迁脚本；dev 仍 SQLite、生产切 Postgres。召回仍全量注入。
- [ ] **Phase 2｜embedding 列 + 写入算向量（影子）**
      加 `embedding` 列 + pgvector 索引；`save_memory`/`approve` 时算向量存入；**召回仍全量**（只写不算），观察 embedding 质量和耗时。
- [ ] **Phase 3｜召回切 top-k 语义**
      `list_memory_contents(query=...)` 上线；小集合回退全量；embedding 失败回退全量。加埋点对比「全量 vs top-k」的回答质量。
- [ ] **Phase 4｜forgetting**
      开 `last_used_at` 更新 + `disable_after_days` 软禁用 + `confidence` 衰减；管理 API 可看/复活。
- [ ] **（并行）长会话 prefill 压缩** —— 按 §9 另立专项。

> **一句话总结**：六阶段、每阶段都能独立回退；先抽象、再换底、再加向量、再切召回、最后 forgetting；长会话并行另做。

## 11. 风险与回退

| 风险 | 缓解 |
|---|---|
| embedding 服务挂 / 慢 | fail-open：写留空补、召回回退按时间；加超时 + 熔断 |
| 语义召回质量差 | 小集合回退全量；Phase 3 加质量对比埋点，不达标不切 |
| Postgres 在某客户环境不可用 | `backend: sqlite` 回退（backend 抽象就是这条退路） |
| 迁移漏数据 | 平迁后行数校验 + 抽样核对；旧 SQLite 保留 N 天再清 |
| 违反「无出站」 | embedding 强制本地；CI 加规则禁 import 云端 embedding SDK |
| 破坏 prompt cache | 记忆只动 ephemeral_system_prompt（本就是），不碰 cached prompt |

## 12. 验收与测试

- **单元**：`MemoryBackend` 两实现的 save/recall/list/delete 行为对齐（同一组用例跑 SQLite + Postgres）。
- **集成**：embedding fail-open 路径（mock 模型抛错 → 写入仍成功、召回回退全量）。
- **迁移**：构造一个有 N 条记忆的 SQLite，平迁后行数、内容、embedding 非空率校验。
- **语义质量**：构造 20 组「用户问题 + 应命中的记忆」对，测 top-k 命中率（baseline = 全量注入）。
- **不变量**：CI 守「不新增 HERMES_* 行为 env」「embedding 不 import 云端 SDK」「`.env` 只放 secret」。

---

## 13. 不在本期范围

- LLM 自动抽取记忆（现在靠人审批候选，足够合规；自动抽取是后续增强）。
- 图数据库 / 实体关系查询（等记忆真长出实体-关系再加 Postgres+AGE）。
- 跨用户/跨租户记忆（to-B 单租户，按 `user_id` 隔离即可）。
- 长会话 prefill 压缩（§9，另立专项）。

---

> **一句话总结（全方案）**：保留「人审批」、换底到 Postgres+pgvector、加本地 embedding、检索从全量注入切到「小集合全量 / 大集合 top-k」语义召回；六阶段可回退落地；长会话压缩另开专项。
