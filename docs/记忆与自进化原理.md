# Part 1 ｜记忆机制

## 它要解决什么问题

一个每次对话都「失忆」的 agent 是笨的——你已经告诉过它你用 Mac、你偏好 Excel、你的项目用 uv 不用 pip,下一轮它全忘,重新问、重新犯错。

**记忆机制就是解决一件事:让 agent 把「值得长期记住的东西」带进以后的每一次对话。**

但「记住」这件事看似简单,真做起来有三个绕不开的设计抉择——记忆机制的原理,全在这三个抉择里。

## 抉择一:谁决定「该记什么」?

这是最关键的原理。三种选择,三种哲学:

| 做法 | 问题 |
|---|---|
| **agent 全自动记**(LLM 自己抽事实) | 它可能记错、记噪音、记隐私;你没法审计它偷偷记了啥 |
| **用户手动一条条记** | 安全、可审计,但太累,没人愿意干 |
| **人在环里**(候选 + 审批) | 系统不擅自决定,但也不让你累 |

**to-B 选了第三种**,原理是:**系统永远不替你决定「这值得记」,但它把原料准备好,等你点头。**

具体怎么落地——每一轮对话结束,系统把这轮原样存成一张「候选条」(pending),不直接进记忆。等以后某个时刻,前端弹给你看「这轮要不要记住?」,你点 approve,它才真正进记忆库;不点就丢。

> 类比:不是装个录音笔啥都录下来(吓人、还录错),也不是让你拿本子手抄(太累);而是**每轮给你一张可撕的便签,你挑想留下的撕进相册,其余丢掉**。

> ⚠️ 注意:现在**没有**「LLM 自动抽事实」这一步——候选条就是整轮对话原文,不是 AI 提炼出的「事实」。所以「自动记忆」目前是名不副实的,真正拍板的还是人。

## 抉择二:记忆放哪、怎么不串号?

10–50 个员工共用一个系统。张经理的记忆绝不能漏给李经理。原理:**记忆按人隔离,一份人一份库**,`user_id` 就是那道墙。

放哪?**全本地、不上云**。这是 to-B 的硬约束(客户数据不出客户机房)。现在是一块本地 SQLite(`memory.db`),未来会迁到客户的 Postgres。

> 类比:每个员工一个带锁的日记本,全锁在客户自己公司的柜子里,不寄到外面。

## 抉择三:怎么让模型「看到」记忆,又不破坏对话?

这里有个容易踩的坑。agent 的「系统提示」(system prompt)在一段对话里是**不能变的**——变了,缓存失效,每轮成本翻倍(这是项目的铁律)。

那记忆怎么塞进去?原理:**记忆不揉进「固定」的系统提示,而是每次请求临时贴一张「贴纸」上去。**

每次 `/chat` 请求来,系统临时把该用户的记忆拼成一截文字,贴在系统提示后面发出去;**这次请求结束,贴纸撕掉,不落库、不改固定提示**。所以模型每轮都看得到你的记忆,而那段「神圣不可变」的提示一个字节都没动。

> 类比:系统提示是印好的「员工手册」(不能改),记忆是每次开会前**临时夹进去的一页便签**(写你这个人最近的事),开完会就拿掉。手册不变,便签每场会现写。

## to-B 现在的记忆长这样(一句话)

> 每个用户一本本地日记本(`memory.db`),**只收你审批过的条目**;每次对话开始,把你的日记**临时贴进**提示里给模型看一眼。

## 🔧 Part 1 技术细节补充

### 数据模型:两张表(`server/memory.py:33`)

库文件:`$HERMES_HOME/memory.db`(SQLite)。

```sql
-- 确认过的持久记忆
memories(
  id          TEXT PRIMARY KEY,     -- uuid
  user_id     TEXT NOT NULL,
  content     TEXT NOT NULL,        -- 一段纯文本(没有结构化字段、没有向量)
  created_at  REAL NOT NULL         -- epoch 秒
)
INDEX idx_memories_user ON memories(user_id)

-- 待审批的候选(每轮对话自动落这)
memory_candidates(
  id, user_id, session_id,
  user_message, assistant_message,  -- 整轮对话原文(不是抽取的事实)
  status,                            -- pending / approved / rejected
  created_at, decided_at, memory_id  -- memory_id 指向 approve 后生成的 memories.id
)
INDEX idx_memory_candidates_user_status ON (user_id, status, created_at)
```

### 两条写入路径(函数级)

| 路径 | 入口 | 落到哪 |
|---|---|---|
| **显式存** | `POST /memory` → `save_memory(user_id, content)` | 直接进 `memories` |
| **候选审批** | 每轮 `/chat` 结束 → `server/routes/chat.py:123` 调 `save_memory_candidate(...)` → `status=pending` → 用户在前端 approve → `approve_memory_candidate()` 提升 | `memory_candidates` →(approve)→ `memories` |

`approve_memory_candidate` 的状态流转:把候选标 `status='approved'`、记 `decided_at`、生成一条 `memories` 并回填 `memory_id`。`delete_memory_candidate` 走 rejected/丢弃。

### 读取与注入(为什么 cache 安全)

`server/agent_factory.py:55`:
```python
memories = list_memory_contents(user_id)        # SELECT content ... WHERE user_id=? ORDER BY created_at DESC
if memories:
    parts.append("Persistent memory about this user (carries across sessions):\n"
                 + "\n".join(f"- {m}" for m in memories))
ephemeral = "\n\n".join(parts)
# → 传给 AIAgent(ephemeral_system_prompt=ephemeral, skip_memory=True)
```
关键:**全量拉、拼成 ephemeral_system_prompt、不落库、不进消息列表**。它贴在 `_cached_system_prompt` 后面每次现拼——所以 `_cached_system_prompt` byte-stable,prompt cache 不破。

### 隔离

所有查询带 `WHERE user_id=?`;`delete_memory` 也校验 `id AND user_id`(防越权删别人)。同一个 user_id 边界和 sessions/users/audit 一致。

### 现在的记忆**没有**这些(为未来留的空)

- ❌ LLM 自动抽取事实(候选就是原文)
- ❌ embedding / 语义检索(全量注入)
- ❌ 置信度 / 衰减 / TTL(只增不减,除非手删)
- ❌ 结构化字段(kind/confidence/source)

> 这些「缺口」正是 [`语义记忆落地方案.md`] 要补的。

> **一句话总结(记忆·技术)**:两张 SQLite 表(`memories` + `memory_candidates`),两条写入路(`save_memory` 显式 / `save_memory_candidate`→`approve` 审批),读取全量拉成文本拼进 `ephemeral_system_prompt`;按 `user_id` 隔离;没有 embedding/TTL/自动抽取——这些是未来增量。

# Part 2 ｜自进化机制(curator)

## 它要解决什么问题

agent 用久了,会给自己攒一堆 **skill**(小 playbook,「遇到 X 该怎么做」)。时间一长,这个 skill 库会**烂掉**:同一个主题写了三个差不多的小 skill、过时的没人清、一次性的占了位。

**自进化机制就是让 agent 自己「打理」它的 skill 库,让它越用越好,而不是越用越乱。**

注意它进化的对象是 **skill**(agent 自己的能力包),**不是用户记忆**——这俩别混(记忆是 Part 1 的事)。

## 核心原理一:两段式 —— 便宜的事自动做,贵的事可选

这是最核心的设计思想。打理 skill 库有两种活,成本和性质完全不同,所以**分开**:

**第一种:图书管理员(免费、规则、默认开)**

不用 AI,就是几条时间规则:
- 90 天没人翻的 skill → 上架收起来(archived,进 `.archive/`)
- 30 天没动的 → 标记「陈旧」(stale)
- 最近又被人用过的 → 从「陈旧」恢复成「活跃」

这条不花一分钱、不调任何模型,纯粹按时间戳搬状态,**默认就开**。

**第二种:编辑(贵、AI、默认关)**

派一个 AI 去读整个库,做**有判断的整理**:发现「这五个小 skill 讲的是同一类事」,就把它们**合并成一个「伞形」大 skill**(类级知识),把零碎的小条目降级成它的参考资料。

这个要调模型、要花钱、且带主观判断,所以**默认关掉**,想用再开。

> 这条原理的价值:**「自动做那些安全又便宜的事,把贵且主观的事留给人类开关」**。

> 类比:整理书架——「积灰的收进储藏室」这事儿雇个保洁阿姨按规矩干就行(便宜、自动);但「这三本其实讲一回事、并成一本」需要个懂行的编辑来定(贵、可选)。

## 核心原理二:只整理,绝不破坏

这是整套机制最讲究的地方——**它被设计成「永远不摧毁用户价值」**。五条铁律:

1. **只归档,不删除**。收起来的 skill 进 `.archive/`,能恢复;绝不会真删(回收站,不是碎纸机)。
2. **只动 agent 自己造的 skill**。用户装的、内置的 skill 一律不碰。
3. **你钉死的(pinned)碰都不碰**。
4. **定时任务(cron)依赖的 skill 不碰**(别人手里正在用的,收走会出事)。
5. **动手前先拍照**——整理前先给整个库拍快照,搞砸了能整体回滚。

> 这条原理是:**一个在后台自动改你东西的系统,必须先证明它改不坏**。

## 核心原理三:空闲时悄悄做

它**不在你用的时候跑**,也不挂个定时器硬跑。原理:**等 agent 闲着、且离上次整理过了很久(默认 7 天),才悄悄动一次**。

而且整理用的是**便宜的辅助模型**(auxiliary),绝不用你正在聊天的主模型——**整理发生在后屋,不在你办公的桌上**,所以不会污染你对话的上下文缓存。

## to-B 现在它睡着(一句)

代码完整、设计漂亮,但 to-B 无头服务里**没通电**——触发入口在交互式 CLI 里。原理都在,只差接电源。

## 🔧 Part 2 技术细节补充

### skill 的生命周期状态(`tools/skill_usage.py:53`)

```
STATE_ACTIVE  →  STATE_STALE  →  STATE_ARCHIVED     (随老化推进)
              30天没动          90天没动,移进 .archive/
pinned = True  → 三状态都不动(正交豁免位)
```

每个 skill 一条记录,字段:`use_count` / `view_count` / `patch_count` / `last_used_at` / `last_viewed_at` / `last_patched_at` / `created_at` / `state` / `pinned` / `created_by`。
**`last_activity_at`** = `max(last_used, last_viewed, last_patched)`(派生的「最近活动」锚点)。

**守门**:`is_agent_created(skill_name)`——整套只动 agent 自己造的;内置/外部目录的只读。

### 配置默认值(`agent/curator.py:56`)

| 常量 | 默认 | 含义 |
|---|---|---|
| `DEFAULT_INTERVAL_HOURS` | 7 天 | 距上次整理超过这么久才考虑跑 |
| `DEFAULT_MIN_IDLE_HOURS` | 2 小时 | agent 至少空闲这么久才跑 |
| `DEFAULT_STALE_AFTER_DAYS` | 30 天 | 没动这么久 → stale |
| `DEFAULT_ARCHIVE_AFTER_DAYS` | 90 天 | 没动这么久 → archived |
| `DEFAULT_CONSOLIDATE` | `False` | LLM 伞形合并默认关 |

### 第一段:确定性状态机(`apply_automatic_transitions`,纯函数无 LLM)

伪代码(`curator.py:291`):
```
stale_cutoff   = now - 30天
archive_cutoff = now - 90天
cron_refs      = _cron_referenced_skills()       # cron 引用的 skill 名(含暂停的)

for skill in agent_created_skills:               # 只 agent 自造的
    if pinned:                       continue    # ① pinned 豁免
    if name in cron_refs:            continue    # ② cron 依赖豁免
    if 没记录过:  seed_record_if_missing; continue # ③ 首次见,种基线(时钟锚 now)

    anchor = last_activity_at 或 created_at 或 now

    if use_count==0 且 anchor > stale_cutoff:    # ④ 从未用 + 年轻 → 宽限
        if state==stale: 设回 active             #    (没用过≠没用,可能还没遇到触发)
        continue

    if   anchor ≤ archive_cutoff:                archive()       # 90天 → 归档
    elif anchor ≤ stale_cutoff 且 active:        set_state(stale)# 30天 → 陈旧
    elif anchor >  stale_cutoff 且 stale:        set_state(active)# 又被用 → 复活
```

**四个豁免各解决一个具体坑**:pinned(用户保的)、cron(下次 fire 要加载)、never-used-young(absence of evidence ≠ evidence of staleness)、seed-if-missing(否则内置一开 prune 就被批量归档)。

### 第二段:LLM 伞形合并(`run_curator_review` → `_llm_pass`,opt-in)

`consolidate=True` 时,fork 一个 **auxiliary AIAgent**(便宜模型,绝不碰主会话 cache),给它 `skill_manage` 工具,跑 `CURATOR_REVIEW_PROMPT`(`curator.py:403`)。

评审 prompt 的「哲学」要点(原文):
- 目标 = **LIBRARY OF CLASS-LEVEL INSTRUCTIONS**,不是「一个 session 一个 skill」(那是库的失败)。
- 门槛不是「两两是否重叠」,而是 **「维护者会写成 N 个,还是 1 个带子节的?」**。
- `use_count=0` 不是该删的理由(新 skill 可能还没遇到触发)。

三种合并方式:
| 方式 | 何时 |
|---|---|
| 并入已有伞形 | 簇里已有一个够宽的 → patch 它加子节,归档兄弟 |
| 新建伞形 | 没一个够宽 → `skill_manage create` 写个 class-level,归档窄兄弟 |
| 降级为支撑文件 | 窄但有值 → 挪进伞形的 `references/`(笔记)/`templates/`(样板)/`scripts/`(脚本) |

`skill_manage` 工具能做的动作(`tools/skill_manager_tool.py`):`create / edit / patch / delete / write_file / remove_file`。

### 安全 + 容错(代码里处处体现)

| 机制 | 实现 | 防什么 |
|---|---|---|
| 只归档不删 | `archive_skill()` 移目录进 `.archive/` | 删了不可逆 |
| pre-run 快照 | `curator_backup.snapshot_skills(reason="pre-curator-run")` | LLM 搞砸能回滚 |
| pinned/cron/内置 豁免 | 状态机 + candidate 列表过滤 | 保住承重 skill |
| auxiliary 模型 | `_resolve_review_runtime()` 走辅助 client | 不碰主会话 prompt cache |
| 先存 state 再跑 LLM | `.curator_state` 在 LLM 前写 `last_run_at` | 崩了不会立刻重触发 |
| `maybe_run_curator` never raises | 全 try/except | 整理任务绝不崩主程序 |
| dry-run | `hermes curator run --dry-run` | 只出报告不真改 |

`.curator_state` 持久化字段:`last_run_at` / `run_count` / `last_run_summary` / `last_run_duration_seconds` / `last_report_path` / `paused`。

### 触发链(`maybe_run_curator`,`curator.py:1958`)

```
should_run_now():  enabled && !paused && (now - last_run_at) ≥ 7天   (首次种基线、等一个 interval)
maybe_run_curator(idle_for_seconds):
    if !should_run_now():              return
    if idle_for_seconds < 2小时:        return     # 调用方测了空闲才传
    run_curator_review()                            # never raises
```
**to-B 里 `maybe_run_curator` 只被 `cli.py:13083` 调**,server/agent_factory 都没调——这就是「没通电」的根因。

> **一句话总结(自进化·技术)**:skill 三态(active/stale/archived)+ pinned 正交豁免;第一段确定性状态机按 30/90 天搬、pinned/cron/年轻-没用 四豁免、纯时间戳无 LLM;第二段 opt-in 的 auxiliary LLM 伞形合并(create/patch/demote);靠 `只归档+pre-run 快照+先存 state+never raises` 保「改不坏」;`maybe_run_curator` 仅 CLI 调 = to-B 未通电。

# Part 3 ｜MemoryProvider 那套高级记忆系统(详解)

> 就是前面 Part 1 提到、被 to-B 关掉(`skip_memory=True`)的「花哨版」。它代码完整、设计考究,值得单独讲透——既是理解上游记忆设计的好教材,也是未来做语义记忆时要不要复用的决策依据。

## 3.1 它是什么:一个「插件化记忆架构」

一句话:**把「agent 怎么记住东西」抽象成一个可插拔的接口(ABC),内置一个文件式实现,允许接外部语义/图记忆后端。一个编排器统一管,只许装一个外部后端。**

它不是某一个记忆库,而是一套**记忆的骨架**——规定「一个记忆后端该实现哪些方法、在对话的哪些时刻被调用」,具体存哪(文件/云图/向量库)由插进来的 provider 决定。

## 3.2 三层结构

```
MemoryProvider(ABC)              ← 契约:每个记忆后端要实现什么(agent/memory_provider.py)
        ↑ 实现
MemoryManager                    ← 编排器:唯一集成点,串进 AIAgent(agent/memory_manager.py)
   ├─ builtin provider           ← 内置实现:MEMORY.md + USER.md 文件式(tools/memory_tool.py)
   └─ 外部 provider(最多 1 个)  ← Honcho / Mem0 / Hindsight 等(to-B 已全删)
```

**关键约束**(`memory_manager.py:6`):同一时间**只允许装一个外部 provider**——多了会「工具 schema 膨胀 + 多后端互相冲突」。

## 3.3 ABC 契约:一个 provider 必须实现什么

分**核心生命周期**和**可选钩子**两类(`agent/memory_provider.py`):

### 核心 lifecycle(必填)

| 方法 | 何时被调 | 干啥 |
|---|---|---|
| `is_available()` | agent 启动 | 检查配置/依赖是否就绪(不发网络请求) |
| `initialize(session_id)` | 启动一次 | 建连接、建表、起后台线程 |
| `system_prompt_block()` | 拼系统提示时 | 返回**静态**说明文字(如「你已接入 Honcho」) |
| `prefetch(query)` | **每轮调模型前** | 返回召回的相关上下文,注入本轮 |
| `queue_prefetch(query)` | 每轮结束后 | 排个**后台召回**,结果给下一轮 prefetch 用 |
| `sync_turn(user, asst)` | 每轮结束后 | 把这轮写进后端(要求非阻塞) |
| `get_tool_schemas()` | 装配工具时 | 暴露给模型的工具(如 `memory_search`) |
| `handle_tool_call()` | 模型调它的工具时 | 执行并返回结果 |
| `shutdown()` | 退出 | 冲队列、关连接 |

### 可选钩子(按需 override)

| 钩子 | 触发点 | 解决什么 |
|---|---|---|
| `on_turn_start()` | 每轮开始 | 计数、周期性维护 |
| `on_session_end(messages)` | 会话真结束 | LLM 抽取事实写进记忆 |
| `on_session_switch(new_id)` | `/resume`、`/branch`、压缩换 session_id | 切换 per-session 缓存状态 |
| `on_pre_compress(messages)` | **上下文压缩前** | 从要被压掉的消息里**抢救**事实 |
| `on_memory_write(action,target,content)` | 内置 memory 工具写入时 | **镜像**一份到外部后端 |
| `on_delegation(task,result)` | 子 agent 完成(父侧) | 观察「派了啥、回来了啥」 |
| `backup_paths()` | `hermes backup` 时 | 声明 HERMES_HOME 外的路径,防备份遗漏 |

## 3.4 怎么接进对话循环(三段式)

这是理解它的关键——记忆不是「一个被动仓库」,而是**三个时刻**主动插进对话循环:

```
[每轮开始]
  manager.prefetch_all(user_message)
    → 各 provider 用「上一轮 queue_prefetch 攒好的结果」返回相关上下文
    → 注入本轮 messages
[模型跑、调工具、出回答]
[每轮结束]
  manager.sync_all(user_msg, assistant_response)    → 各 provider 把这轮写进后端(后台线程)
  manager.queue_prefetch_all(user_msg)              → 排后台召回,给「下一轮 prefetch」预热
```

精髓:**prefetch 用的是「上一轮排的召回」**——把召回延迟(尤其云后端)藏进用户思考的间隙,不拖慢本轮。这是这套架构最聪明的地方。

## 3.5 内置 builtin:MEMORY.md + USER.md 文件式

外部 provider 没装时,用内置文件式(`tools/memory_tool.py` 的 `MemoryStore`),落在 `$HERMES_HOME/` 下两个文件:

| 文件 | 存什么 |
|---|---|
| **MEMORY.md** | agent 的**个人笔记/观察**:环境事实、项目上下文(如「这仓库用 uv 不用 pip」) |
| **USER.md** | agent 对**用户**的认知:偏好、沟通风格(如「张经理喜欢简洁、不要客套」) |

文件是**散文**,按 `§` 分段成一张张「卡」(card)。

**自动写入路径**:`agent/background_review.py` 的 `_MEMORY_REVIEW_PROMPT`——后台起一个 auxiliary AIAgent,评审「这轮有没有值得长期记的」,有就写进 MEMORY.md/USER.md。这就是 AIAgent 类里 `_spawn_background_review(review_memory=True)` 干的事。

> ⚠️ 注意:这套「LLM 自动抽取写文件」是**主动的、后台的、无人工审批**——和 to-B 现用的「候选→人审批」哲学**正好相反**。这也是 to-B 关掉它的原因之一(合规/可审计)。

## 3.6 外部 provider(云/图记忆)

上游支持接外部语义/图记忆后端:**Honcho、Hindsight、Mem0**。装在 `plugins/memory/<name>/`,实现上面那个 ABC。

- **单外部 provider 限制**:装第二个会被拒,防工具 schema 膨胀 + 多后端打架。
- **to-B 现状**:`plugins/memory/` 目录只剩 `__init__.py`,**8 个云 provider 在改造 Step 2.3 全删了**(决策 7:无云记忆)。ABC 留着,是给「未来可能写个本地 provider」留口子。

## 3.7 learning_graph(可视化层,别和记忆本体混)

`agent/learning_graph.py` **不是记忆存储**,是个「让学习可见」的可视化层:把 MEMORY.md/USER.md 的 card + 已学 skill 当成**图节点**,用词法重叠派生「记忆 ↔ 技能」的链接。是给桌面 UI 画图用的,跟 to-B 无头服务无关。

## 3.8 to-B 为什么把整套关了(`skip_memory=True`)

四个原因,每条都硬:

1. **云 provider 违反硬约束**:Honcho/Mem0 要把数据发云端,直接违反决策 7(无云记忆 / 无出站遥测)。
2. **builtin 文件式不适合多用户**:MEMORY.md/USER.md 是**单用户、单进程**的(一份文件、一个 agent 实例)。to-B 是 10–50 用户共享一个 server、每请求新建 agent——文件式没法按 `user_id` 隔离。
3. **gateway 没了**:这套是给 CLI/gateway 长会话设计的(一个 agent 跑很久、跨多轮慢慢积累);无头服务每请求新 agent,没有「长生命周期 agent」这个前提,大半钩子(`on_session_switch`/`on_delegation`/`on_pre_compress`)用不上。
4. **per-turn 后台评审成本**:每轮起 auxiliary 模型评审「记不记」,高并发下成本和延迟都不划算——而且是无人工审批的自动写,合规上 to-B 不接受。

所以 to-B 换成了 `server/memory.py` 的 per-user SQLite + 显式存/候选审批——**更笨但更合适**。

## 3.9 如果未来要复活,怎么走?

**不建议直接开 `skip_memory=False`**(那会把单用户文件式 + 自动抽取 + 每轮 aux 评审全放出来,跟 to-B 多用户/合规/成本全打架)。

**正确姿势**:基于 `server/memory.py` 加 embedding 做语义召回,不走这套 ABC——理由是 ABC 的「per-agent 长生命周期」假设跟 to-B「每请求新 agent」不兼容。完整方案见 [`语义记忆落地方案.md`]。

**只有一种情况考虑复活 ABC**:to-B 以后真跑**长生命周期 agent**(每用户一个常驻「客户经理 agent」,或复活 kanban/swarm)——那时 ABC 的生命周期钩子才值钱。但那是另一种产品形态。

> **一句话总结(MemoryProvider)**:一套「ABC 契约 + 单外部 provider 编排器 + builtin 文件式(MEMORY.md/USER.md)+ 可选云图后端」的插件化记忆架构,在对话的每轮开始/结束、压缩前、换会话、派子任务等关键点用钩子主动介入(prefetch 召回 / sync 写入 / 抢救事实 / 镜像写入),全程后台非阻塞。to-B 因「无云记忆 + 多用户 + 无长会话 + 成本」四个原因关掉,换简单 per-user SQLite;未来做语义记忆应基于 `server/memory.py` 扩展,不走这套 ABC。

# 全篇总结

| | 记忆机制(to-B 活) | 自进化机制(to-B 睡) | MemoryProvider(关掉) |
|---|---|---|---|
| 管的是 | 对**用户**的认知 | agent 自己的 **skill 库** | 对用户/环境的认知(可接云) |
| 核心原理 | 人审批 + 本地隔离 + 临时注入 | 两段式(便宜自动/贵可选)+ 只整理不破坏 + 空闲做 | ABC 插件化 + 三段式介入 + 单外部 provider |
| 存储 | `memory.db`(SQLite) | `.curator_state` + `skills/` | MEMORY.md/USER.md(文件) |
| 触发 | 每轮 /chat + 审批 | 空闲 + 7 天(现仅 CLI) | 每轮 prefetch/sync |
| to-B 状态 | **活**(简版) | **睡**(代码完整,未通电) | **关**(`skip_memory=True`) |
| 共同底色 | 本地、不破坏对话缓存、可回退可审计 | 同左 | (设计同左,但被 to-B 多用户/合规约束否决) |

> **一句话总结(全篇)**:**记忆**回答「agent 怎么记住用户」——靠人审批 + 本地隔离 + 临时注入(活);**自进化**回答「agent 怎么打理自己的能力库」——靠两段式 + 只整理不破坏 + 空闲悄悄做(睡);**MemoryProvider** 是上游那套被关掉的插件化记忆架构,设计考究但跟 to-B 多用户/无云/每请求新 agent 不兼容,未来语义记忆应基于 `server/memory.py` 扩展而非复活它。
