# 知识库构建方案（企业知识库 · 多库三步流程）

> 范围：**只做"知识库构建"**——建库 → 文档上传 → 解析 → 分块 → embedding → 写入 ES + Milvus。
> 本期**不做** RAG 检索问答、**不做**个人知识库、**不支持** html。
> 个人库与检索问答为二期范围，本文档的结构（tenant 字段、chunk 主键、chunk 上的 `kb_id` 冗余、sync 幂等）已为其预留。

## 1. 总体架构

知识库按**显式三步**操作（一期"单一隐式库、上传即解析"的决策已作废）：

```
① 新建知识库（admin）        knowledge_bases 表，(tenant_id, name) 唯一
② 上传文档（admin, multipart）
  → server/routes/knowledge.py            # 校验 + 落盘 + 建行（status=uploaded），202 立即返回
  → $HERMES_HOME/knowledge/files/<uuid><ext>   # 原始文件（本地盘）
  → knowledge_documents(uploaded)              # MySQL；不入队、不动 pipeline
③ 勾选文档 → POST /documents/parse（admin，批量）
  → knowledge_documents(pending) + knowledge_jobs(queued)   # 只对 uploaded/failed 入队
  → Redis 队列（knowledge: 前缀，runtime.py）
  → hermes-knowledge-worker 容器消费
      pipeline:  parse → chunk → replace_knowledge_chunks（MySQL=事实源）
      sync:      embed → ES bulk → Milvus insert（幂等 delete-then-write）
  → status: uploaded → pending → parsing → syncing → ready / failed

前端轮询（React Query refetchInterval 3s），不走 SSE。
普通用户只读（含 uploaded/failed 文档）；建库/上传/解析/删除/重试仅 admin。
```

设计要点：

- **MySQL 是事实源，ES/Milvus 是投影。** chunk 先落 `knowledge_chunks` 表，再同步到两个检索引擎；同步失败可重试，重放是幂等的（按 `doc_id` 先删后写）。
- **上传与解析解耦。** 上传接口只做校验+落盘+建行，202 返回 `{document}`（status=`uploaded`）；解析由 `POST /knowledge/documents/parse` 显式批量触发。pipeline 入口有守卫：非 `pending` 状态的文档直接拒跑（`DocumentNotPendingError`），`uploaded` 文档绝不可能被隐式构建。
- **与 Agent 运行共用一套队列原语。** `server/storage/runtime.py` 里 knowledge 系列的 enqueue/claim/heartbeat/finish/requeue 完全镜像 agent_job 那套（Redis Lua / 进程内 deque 双实现），无 Redis 时可用内嵌 worker 兜底（见 §7）。

## 2. 部署

### 2.1 compose profile `knowledge`

```bash
docker compose --env-file .env.compose --profile app --profile knowledge up -d
```

新增 5 个服务，全部只挂 `hermes-data` 内网、不出网，镜像 tag+digest 双锁定。etcd/minio 不映射宿主机端口；ES/Milvus 各映射一个 **127.0.0.1 回环端口**（`KNOWLEDGE_ES_PORT=19200` / `KNOWLEDGE_MILVUS_PORT=19530`），仅供"server/知识库 worker 跑在宿主机"的 dev 场景直连——全容器化部署时忽略映射、用内网地址：

| 服务 | 镜像 | 说明 |
|---|---|---|
| `elasticsearch` | `docker.elastic.co/elasticsearch/elasticsearch:8.18.4@sha256:…` | single-node，容器内 `http.port=19200`（避开常见 9200 冲突），xpack.security 关，堆 1g/上限 2g |
| `milvus` | `milvusdb/milvus:v2.5.16@sha256:…` | standalone，内网 19530 |
| `etcd` | `quay.io/coreos/etcd:v3.5.21@sha256:…` | Milvus 元数据 |
| `minio` | `minio/minio:RELEASE.2025-09-07T16-13-09Z@sha256:…` | **Milvus 的内部对象存储，与文档存储无关**——文档存本地盘 `$HERMES_HOME/knowledge/files/` |
| `hermes-knowledge-worker` | `hermes-agent-tob:dev`（同服务端镜像） | `alembic upgrade head && python -m server.knowledge.worker` |

MinerU 与 embedding 端点**不在 compose 里**：MinerU 在客户 GPU 服务器上，embedding 调客户自备的 OpenAI 兼容端点，都是内网 HTTP 地址，配置在 `deployment.yaml`。

Dockerfile 增加了 `libreoffice-writer/impress/calc`（headless 转 PDF 用，镜像约 +500MB）。

> **坑**：Milvus 连接 MinIO 的默认凭据是 `minioadmin:minioadmin`，与 MinIO 容器的 `MINIO_ROOT_USER/PASSWORD` 是两套配置。compose 里自定义了 MinIO root 凭据时，**必须**通过 `MINIO_ACCESS_KEY_ID/MINIO_SECRET_ACCESS_KEY` 同步给 Milvus，否则 Milvus 启动即 panic（`The request signature we calculated does not match`）。

### 2.2 deployment.yaml

```yaml
knowledge:
  enabled: true
  mineru_url: http://gpu-server:18888        # 客户 GPU 服务器上的 MinerU
  # api = MinerU FastAPI 封装（POST /file_parse）；vlm = vLLM 裸起的 MinerU2.5
  # 模型服务（OpenAI 兼容），由 mineru-vl-utils 两段式客户端驱动（本地 pymupdf
  # 渲染页图 → 远程版面+识别），解析产物与 api 模式同构
  mineru_mode: api
  es_url: http://elasticsearch:19200         # 容器内网地址（宿主机 dev 用 http://127.0.0.1:19200）
  milvus_uri: http://milvus:19530            # 宿主机 dev 用 http://127.0.0.1:19530
  embedding:
    base_url: http://embedding-server/v1     # 客户自备 OpenAI 兼容端点
    model: bge-m3
    dim: 1024
    api_key_env: KNOWLEDGE_EMBEDDING_API_KEY
    batch_size: 32
  chunk_size: 400
  chunk_overlap: 64
  min_chunk_tokens: 50               # 短于此 token 数的尾块并入前一块（表格块除外）
  max_file_mb: 100
```

`knowledge.enabled=false`（缺省）时整组 `/knowledge` 路由 404，前端显示"当前部署未启用知识库"。

密钥只进 `$HERMES_HOME/.env`：`KNOWLEDGE_EMBEDDING_API_KEY`（+可选 `KNOWLEDGE_ES_PASSWORD`）。
compose 侧只需 `MINIO_ROOT_USER/PASSWORD`（见 `compose.env.example`）。

## 3. 数据模型（MySQL，Alembic 已出 migration）

| 表 | 角色 | 关键字段 |
|---|---|---|
| `knowledge_bases` | 知识库 | name（`(tenant_id, name)` 唯一）、description、creator_id、doc_count/chunk_count（反规范化，repository 维护） |
| `knowledge_documents` | 文档行 | kb_id、status(`uploaded/pending/parsing/syncing/ready/failed`)、error、parser(`mineru/local`)、chunk_count、retry_count、file_path（相对路径） |
| `knowledge_chunks` | 分块事实源 | id（同时是 ES/Milvus 主键）、kb_id（冗余，为按库检索预留）、doc_id、chunk_title（标题路径）、content、doc_pos、token_num、is_use；`UniqueConstraint(doc_id, doc_pos)` |
| `knowledge_jobs` | 构建任务 | status(`queued/running/succeeded/failed`)、attempt、worker_id、heartbeat_at |

四表都带 `tenant_id`（一期恒为 default，二期个人库/多空间直接复用）。

**存量迁移**：Alembic migration 对每个租户自动创建一个「默认知识库」，把既有 documents/chunks 的 `kb_id` 回填进去并对齐计数，再把列改成 NOT NULL；SQLite 路径在 `database.py` 的列补丁块里镜像同样逻辑。上传时若租户一个库都没有，`get_or_create_default_knowledge_base()` 会惰性兜底建库。

## 4. 格式路由与解析（`server/knowledge/parser_client.py`）

| 格式 | 链路 | parser 标记 |
|---|---|---|
| pdf | MinerU 直解（api 模式 = `/file_parse`；vlm 模式 = 页图→OpenAI 兼容 VLM） | mineru / mineru-vlm |
| doc/docx/ppt/pptx/xls | LibreOffice headless 转 PDF → MinerU | mineru / mineru-vlm |
| txt/md | 本地直读（md 的 `#` 层级 → text_level） | local |
| xls/xlsx | openpyxl 直读 → 每 sheet 一个 HTML 表格块 | local |

xlsx **不走** LibreOffice 转 PDF——宽表会被纸张截断，效果差；openpyxl 直读保留完整单元格。
MinerU 不可用时，pdf/office 文档会 failed（error 里带原因）；txt/md/xlsx 不依赖 MinerU。

## 5. 分块策略（`server/knowledge/chunker.py`，纯函数）

两种模式（`knowledge.chunk_mode`，默认 `structural`）：

**structural —— 结构 + token 递归切（零额外消耗）**

1. **结构分段**：`text_level` 标题开新 section，`chunk_title` = 标题路径（` / ` 连接，≤200 字符）。
2. **递归切分**：tiktoken `cl100k_base` 计数，section 超过 `chunk_size`（默认 400 token）按 段落→句子→硬切 递归，`chunk_overlap` 64（取前块尾部 token 前缀）。
3. **短尾合并**：<`min_chunk_tokens`（默认 50 token，两种模式共用）的尾块向前合并（含 `<tr` 的表格块除外，表格保持原子）。
4. **表格**：整块一个 chunk；超过 2×chunk_size 按行切并**重复表头行**，标题追加"（表）"。
5. **噪声**：`page_number`/`page_footnote` 丢弃；图片只保留 caption（`[图] …`）。

**semantic —— 句级 embedding 相似度切分（`semantic_chunker.py`）**

chonkie `SemanticChunker` 的本地化实现（不引 chonkie 依赖；参考项目用的
LateChunker 需要本地 embedding 权重，与远程端点架构冲突，故未采用）：

1. **句子切分**：按 chonkie recipe 模版（`split_templates/default_ch.json`，
   中文分隔符 `。！？；\n`）切句，<24 字符的短句并入前句。
2. **滑窗相似度**：`sim[i] = cosine(embed(第 i..i+3 句拼接), embed(第 i+3 句))`，
   衡量"下一句"是否仍属上文话题；embedding 复用 `knowledge.embedding` 端点。
3. **切点检测**：Savitzky-Golay 一阶/二阶导数找相似度曲线的局部极小值
   （话题切换点），只保留 ≤ `threshold`（0.8）分位数的极小值。
4. **尺寸兜底**：语义组超 `chunk_size` 按句贪心装包硬切。

结构分段、表格原子、短尾合并与 structural 完全一致——semantic 只替换"段内
递归切"那一步，且**无 overlap**（语义块本来就按话题聚合，重叠反而稀释）。
代价：每文档分块时多一轮句级 embedding 调用（句数×2 量级），失败则整篇 failed。

`doc_pos` 全局递增、`token_num` 同 encoding 统计——两者进 MySQL 也进 ES/Milvus，检索期可直接引用。

## 6. 同步与幂等（`server/knowledge/sync_service.py`）

`synchronize_document(doc_id)`：

1. 读 MySQL 里 `is_use=true` 的 chunks；
2. ES `create_index` + `delete_by_term(doc_id)`，Milvus `create_collection` + `delete_by_doc_id`——**先删后写**，重跑/重试安全；
3. embedding（批量，客户 OpenAI 兼容端点）；
4. ES `bulk_insert`（全文 + 元数据），Milvus `batch_insert`（向量 + 标量，content 截 4000 字符）。

ES mapping 与 Milvus schema 都带 `kb_id` 字段（keyword / VARCHAR），同步时从 chunk 冗余写入——二期按库检索直接用它过滤，无需回表。**升级注意**：`kb_id` 是新增字段，已存在的 ES 索引/Milvus 集合需要重建（drop 后对文档逐个 retry 即可，MySQL 是事实源，重放幂等）。

删除文档走 `clear_document(doc_id)`：清两个引擎的投影 → 删本地文件 → 删 MySQL 行。投影清理失败不阻断删除（孤儿数据随索引重建消失，日志记录）。删除知识库是**级联**：`repository.delete_knowledge_base` 先删行并返回库内文档列表，路由层再逐文档清 ES/Milvus 投影与磁盘文件。

## 7. 队列与 worker

- 队列原语在 `server/storage/runtime.py`（`knowledge:` 命名空间），镜像 agent_job：lease 60s、心跳过期 180s 判死、最多 3 次投递。
- `hermes-knowledge-worker` 容器跑 `KnowledgeWorker.run_forever`：周期性 recover（回收过期/僵死 job）→ claim → `run_job` → finish。pipeline 幂等，recovery 直接 requeue。
- **内嵌兜底**：无 Redis 且 `HERMES_ALLOW_EMBEDDED_KNOWLEDGE_WORKER=1` 时，server 进程内起线程跑 `run_once`（开发用）；两者都没有则解析接口返回 503，避免文档卡在 pending。

## 8. API（详见 `docs/API文档.md` §3.9）

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/knowledge/bases` | 登录用户 | 知识库列表（含文档/分块计数） |
| POST | `/knowledge/bases` | admin | 新建知识库（201；同名 409） |
| PATCH | `/knowledge/bases/{kb_id}` | admin | 改名/描述 |
| DELETE | `/knowledge/bases/{kb_id}` | admin | 级联删除库内全部文档（引擎/文件/MySQL） |
| POST | `/knowledge/bases/{kb_id}/documents` | admin | multipart 上传，202 `{document}`（status=uploaded，**不入队**） |
| POST | `/knowledge/documents/parse` | admin | 批量解析 `{document_ids}`，202 `{queued, skipped}` |
| GET | `/knowledge/documents?status=&kb_id=` | 登录用户 | 列表 + stats |
| GET | `/knowledge/documents/{id}` | 登录用户 | 文档详情 |
| GET | `/knowledge/documents/{id}/chunks` | 登录用户 | 分块预览 |
| DELETE | `/knowledge/documents/{id}` | admin | 三处清理（引擎/文件/MySQL） |
| POST | `/knowledge/documents/{id}/retry` | admin | 仅 failed/ready 可重试（409/410 兜底） |

上传安全：文件名剥路径成分、扩展名白名单、`max_file_mb` 大小上限；建行失败即删已落盘文件。建库/删库/上传/解析/删除/重试都写审计（`knowledge_base_create/knowledge_base_delete/knowledge_upload/knowledge_parse/knowledge_delete/knowledge_retry`）。

## 9. 前端（apps/web）

三步流程对应三级视图：

- `components/knowledge/KnowledgeBaseListView.tsx`（步骤①）：知识库表格（名称/文档数/分块数/更新时间），admin 有「新建知识库」弹窗与删除按钮（级联确认提示）；点行进入库详情 tab（`knowledgeBaseDetail`）。
- `components/knowledge/KnowledgeBaseView.tsx`（步骤②③，库详情）：上传（点击或拖拽）只落库为「待解析」，不触发解析；文档表带复选框，admin 勾选后点「解析所选」批量入队（`POST /documents/parse`，回显 queued/skipped 数量）；行级重试/删除不变；面包屑返回库列表。
- `components/knowledge/DocumentDetailView.tsx`：构建状态面板（解析器/分块数/错误 banner）+ 分块预览（标题路径、token 数、内容截断）；顶部面包屑「知识库 / 库名 / 文档」可逐级返回。
- 有 `pending/parsing/syncing` 文档时 `refetchInterval: 3000` 自动轮询，全部终态后停止。
- 基础件（PageHeader/DataTable/Badge 等）下沉到 `components/ui.tsx` 复用；风格沿用既有 token，无新 UI 依赖。
- Chat 右侧栏"知识来源"为真实 ready 文档（`?status=ready`，404 即未启用时显示空态）。

## 11. 二期路线

1. **个人知识库**：`tenant_id`/owner 维度已留好，加 `scope=enterprise|personal` 与 per-user 索引即可。
2. **RAG 检索问答**：ES BM25 + Milvus 向量混合检索已就绪，chunks/ES/Milvus 三处的 `kb_id` 冗余让"按库检索"只需一个过滤条件；差一个检索 tool（建议走 `check_fn` 门控或服务化，按 Footprint Ladder 评估）与 Chat 引用 UI。
3. **html/扫描件 OCR** 等更多格式：parser_client 里加一个路由分支即可。
